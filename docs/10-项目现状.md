# 项目现状

本文回答一个具体问题：**当前这份代码，哪些能跑、哪些不能跑、差在哪里**。所有结论均来自对 `main` 分支源码的逐行核对，附行号可查证。

> 结论先行：**解析 → 调度 → 算子 → 治理接口的主链路已完整可用**。20 个可执行 cellType 全部具备执行器与转换器，Plan 发布/幂等/超时重试/traceId 已落地；主要受限点是 `TaskProductor` 本地直调未真正投递 MQ（无法多实例水平扩容），以及少量健壮性缺陷（见 §3）。

### 2.2 类型解析与路由

前端画布使用统一算子节点 `node_op`，真实类型由 `data.cellType` / `data.opType` 决定。`CellTypeMapper` 负责解析（未命中回退 `node_outer_http`）：

```java
String executeType = CellTypeMapper.resolveExecuteType(task);
Object bean = SpringBeanUtils.getBeanOrNull(executeType);
if (bean instanceof Execute) {
    ((Execute) bean).run(task.getId());
}
```

| 环节 | 实现 | 说明 |
| --- | --- | --- |
| 类型解析 | `parser/CellTypeMapper` | `node_op` + `data.opType` → 真实 cellType |
| 转换器 | `convert/OperatorConverterConfig` | 以 `{cellType}_task` 注册 19 个 `TaskInterface`（实现 `JsonPayloadTask`）|
| 执行器 | `executor/impl` | 20 个 `Execute` Bean，Bean 名即 cellType |
| 兜底 | `TaskRunConsumer` | `getBeanOrNull` 取不到时 ack 跳过（不再 NPE）|

> 历史实现中的「Jar/Python 复用 Shell 执行器」分支已被 `ScriptOperateExecutor` / `PythonOperateExecutor` / `JarOperateExecutor` 三个独立 Bean 取代。

### 2.3 端到端可用性结论

| 场景 | 可用性 | 原因 |
| --- | --- | --- |
| 开始 → 结束 | ✅ 可用 | 两个转换器与执行器齐备 |
| 开始 → 数据映射 → HTTP → 结束 | ✅ 可用 | `OperatorConverterConfig` + `executor/impl` 已覆盖 |
| 任意含条件分支的流程 | ✅ 可用 | 决策线 `dicisionEdges` 赋值缺陷已修复 |
| 任意含循环的流程 | ✅ 可用 | whileDo 判空已修复，并有 `max-loop-times` 保护 |
| 任意含补偿的流程 | ✅ 可用 | 补偿执行器（datamap/http/dubbo/webservice 补偿）齐备 |
| 按 `planId` 运行不同流程 | ✅ 可用 | DSL 取自 `SERVEA_PLAN`，含 `DISABLED` / `require-published` 门禁 |

> **实践建议**：当前可直接端到端验证前端产出的 DSL —— 存模型（`/plan/save`）→ 运行（`/inst/run/or/getResult/{planId}`）→ 观察（`/inst/detail`、`/instlog/list`）。
> 仍受限的是**多实例水平扩容**：`TaskProductor` 为本地直调，未真正投递 MQ（见 §3 缺陷）。
