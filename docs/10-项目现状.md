# 项目现状

本文回答一个具体问题：**当前这份代码，哪些能跑、哪些不能跑、差在哪里**。所有结论均来自对 `main` 分支源码的逐行核对，附行号可查证。

> 结论先行：**流程骨架（解析 → 调度）基本完整，但算子层严重缺失**。24 种节点类型中只有 3 种真正可用，导致除「开始 → 数据映射 → HTTP → 结束」这一条最小链路外的绝大部分流程无法跑通。

**统计：24 种类型中 2 种完全可用，1 种半可用（有执行器无转换器），21 种不可用。**

### 2.2 为什么「有执行器」仍不可用

调度层对每个下一批节点都执行（`TaskResultConsumer` L365）：

```java
TaskInterface ti = SpringUtil.getBean(cell.getCellType() + TaskType.suffix);
Task t = ti.convert(cell, inst);
```

`TaskType.suffix = "_task"`。当前容器中只有两个 Bean：

| Bean 名 | 来源 |
| --- | --- |
| `node_start_task` | `StartTask` |
| `node_end_task` | `EndTask` |

因此**只要相邻节点不是「开始」或「结束」，取 Bean 即失败**。`node_inner_datamap` 与 `node_outer_http` 虽然有执行器，但没有转换器，依然跑不通。

同理，执行器侧（`TaskRunConsumer` L68-72）：

```java
if (Arrays.asList(CellType.FUN_JAR, CellType.FUN_PYTHON).contains(task.getType())) {
    execute = (Execute) SpringBeanUtils.getBean(CellType.FUN_SHELL);
} else {
    execute = (Execute) SpringBeanUtils.getBean(task.getType());
}
```

取不到 Bean 时返回 `null`，后续 `execute.run(...)` 直接 NPE。

### 2.3 端到端可用性结论

| 场景 | 可用性 | 原因 |
| --- | --- | --- |
| 开始 → 结束 | ✅ 可用 | 两个转换器与执行器都在 |
| 开始 → 数据映射 → HTTP → 结束 | ❌ 不可用 | 缺 `node_inner_datamap_task` / `node_outer_http_task` |
| 任意含条件分支的流程 | ❌ 不可用 | 决策线判断逻辑失效（缺陷 #1）+ 缺转换器 |
| 任意含循环的流程 | ❌ 不可用 | 缺转换器；whileDo 另有 NPE 风险 |
| 任意含补偿的流程 | ❌ 不可用 | 缺补偿算子执行器与转换器 |
| 按 `planId` 运行不同流程 | ❌ 不可用 | DSL 硬编码读 `hrh_http.json` |

> **实践建议**：若要在当前代码上验证前端产出的 DSL，只能验证到「解析是否成功」这一步（`DslParser.parser` 可独立调用），无法跑通完整执行链路。

## §3 缺陷清单

按优先级排序。**P0 = 功能完全不可用；P1 = 阻塞主链路；P2 = 特定场景出错；P3 = 健壮性/可维护性。**

| 优先级 | 位置 | 缺陷描述 | 影响范围 | 修复建议 |
| --- | --- | --- | --- | --- |
| **P0** | `TaskResultConsumer` L381-385 | `inputEdges.stream()...collect(Collectors.toList())` 的返回值**未被接收**；`dicisionEdges` 在 L381 被初始化为 `null` 后从未赋值 | 决策线判断恒为假 → 条件分支功能完全不可用 | 把 `dicisionEdges = inputEdges.stream()...` 的赋值补上 |
| **P0** | `convert` 包 | 24 种节点类型中只有 2 个 `TaskInterface` 实现（`node_start_task` / `node_end_task`），缺 22 个 | 除首尾节点外无法转任务，绝大多数节点流转时抛异常 | 按 [算子扩展指南](07-算子扩展指南.md) §3 步骤 3 逐个补齐 |
| **P1** | `executor/impl` 包 | 24 种节点类型中只有 4 个 `Execute` 实现，缺 20 个 | 补偿/Dubbo/WebService/脚本/JSON↔XML 等算子全不可用 | 按 [算子扩展指南](07-算子扩展指南.md) §3 步骤 4 补齐 |
| **P1** | `InstController` L80 | DSL 硬编码 `FileUtil.readUtf8String("hrh_http.json")`，未使用 `planId` | 无法按流程模型运行；多流程无法共存 | 引入 `Plan` 实体与集合，按 `planId` 查 DSL |
| **P1** | `TaskResultConsumer` L334 | whileDo 分支内使用 `outLoopEdges.get(0)`，而该分支中 `outLoopEdges` 可能为 `null` | whileDo 循环触发 NPE | 先判空，或把循环线集合的获取提前到分支外 |
| P2 | `InstController` L178-189 | `get_result` 分支不使用 `servea_instId`，只查本次请求新建的实例 | 无法查询历史实例结果 | 读入 `servea_instId` 并按 id 查库 |
| P2 | `InstController` L210-229 | 文件下载分支中 `fileName` 可能为 `null` 即 `URLEncoder.encode` | 非 JSON 出参且路径为 `filemgr://` 时 NPE | 补判空；并实现下载逻辑（当前为 TODO） |
| P2 | `TaskResultConsumer` L389 | `pSkipNum == skipNodes.size()`，语义上应为 `pSkipNum == pids.size()` | SKIP 传播判断可能失效，导致下游节点误执行或漏执行 | 改为与父节点数量比较 |
| P2 | `TaskProductor` L42 / L49 | `sendTaskRun` / `sendTaskResult` 实为**本地方法直调**，未投递 MQ | 多实例部署时任务不会跨节点分发，无法水平扩容 | 改用 `MqChannelProcessor` 中已定义的通道真正投递 |
| P2 | `DataMapOperateExecutor` L283 | `jsonObject.equals(expression)` 疑似应为 `jsonObject.containsKey(...)` | 上游节点取值分支可能失效 | 按意图修正为 `containsKey` |
| P3 | `DslParser` L261 / L278 | 递归出口用 `static` 计数器 `Chilednum` / `Parentnum` | 并发调用 `parser` 时结果错误 | 改为方法参数传递 |
| P3 | `DslParser` L33 / L139 / L152 | `Optional.get()` 未判空 | DSL 缺首尾节点时抛 `NoSuchElementException`，错误信息不友好 | 加 `orElseThrow(() -> new BizException("缺少开始节点"))` |
| P3 | `TaskType` L25-47 | 除 `START` / `END` 外常量被整体注释 | 可读性差，全靠 `cellType + "_task"` 约定，易出错 | 恢复常量定义并在 `convert` 中显式声明 |
| P3 | `HttpTaskExecutor` L140-147 | 文件下载为 TODO，`fileList` 恒为空 | 文件上传功能不可用 | 实现文件读写 |
| P3 | `InstLog` | 日志级别常量拼写为 `LEVEL_ERRO`（缺 `R`） | 命名不规范，易误用 | 重命名并保留兼容别名 |
| P3 | `Inst` | 时间字段拼写为 `starDate`（应为 `startDate`） | 字段名错误，前端需特判 | 重命名（注意 Mongo 已有数据兼容） |
| P3 | `RegisterInfoEntity` | 字段 `sheelFtpPath`（应为 `shellFtpPath`） | 拼写错误 | 重命名 |
| P3 | `Inst.syncInstMap` | 静态 Map 已定义但从未使用 | 死代码 | 删除或落实同步等待逻辑 |
