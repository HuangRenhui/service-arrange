## §1 测试策略

### 1.1 分层测试金字塔（目标态）

```
        ┌─────────────────┐
        │  端到端（E2E）   │  流程编排 → 运行 → 校验出参
        └─────────────────┘
      ┌───────────────────────┐
      │   集成测试             │  DslParser / 调度链路 / 接口
      └───────────────────────┘
    ┌─────────────────────────────┐
    │        单元测试              │  表达式求值 / Schema 工具 / 校验规则
    └─────────────────────────────┘
```

### 1.2 当前可测范围

| 层次 | 可测性 | 说明 |
| --- | --- | --- |
| 前端校验规则 | ✅ 易测 | `DslValidator.validate()` 是纯函数，可直接单测 |
| 表达式求值 | ✅ 可测 | `TaskServiceImpl#edgeDecisionDo` 逻辑独立，但需 mock 实例数据 |
| DSL 解析 | ✅ 可测 | `DslParser#parser` 输入字符串输出 `Inst`，是最佳切入点 |
| Schema 工具 | ✅ 可测 | `JsonSchemaUtil` 纯函数 |
| 调度链路 | ⚠️ 难测 | 依赖 Mongo + MQ + ZK，需集成环境 |
| 算子执行 | ⚠️ 部分可测 | `DataMapOperateExecutor` 逻辑可测；HTTP 算子需 mock |
| 端到端 | ✅ 可测 | 执行器与转换器齐备，主链路可跑通；回归项见 §6 |

### 1.3 补测优先级建议

| 优先级 | 测试对象 | 理由 |
| --- | --- | --- |
| 1 | `DslParser` | 引擎入口，图构建正确性决定一切；纯函数易测 |
| 2 | `DslValidator`（前端） | 纯函数，覆盖 R1~R11 全规则 |
| 3 | `TaskServiceImpl` 表达式求值 | 决策/循环的正确性核心 |
| 4 | `JsonSchemaUtil` | 入参类型还原依赖它，边界多 |
| 5 | `DataMapOperateExecutor` | 取值逻辑分支多，易出边界 bug |
| 6 | 调度链路集成测试 | 需引入 testcontainers 或嵌入式 Mongo |

## §3 解析层验证

`DslParser` 是最值得优先补测的组件。以下用例可直接转成 JUnit。

### 3.1 基础图构建

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| 最简流程 | 开始 → 结束 | `roots = [startId]`；`nodeChildsMap[startId] = {endId}` |
| 线性三节点 | 开始 → A → 结束 | A 的 parent = `{startId}`；end 的 parent = `{A}` |
| 多分支 | 开始 → A、开始 → B | 两者 parent 均为 `{startId}` |
| 汇聚 | A → C、B → C | C 的 parents = `{A, B}` |
| 孤立节点 | 一个不与任何线相连的节点 | 同时进入 `roots` 与 `ends` |

### 3.2 真实入口/出口推导（对齐 `DslParser` L79/L82）

| 用例 | 连线 | 期望 `roots`（真实入口） | 期望 `ends`（真实出口） |
| --- | --- | --- | --- |
| 线 1-2、2-3 | src={1,2}，tar={2,3} | `{1}` | `{3}` |
| 线 1-2、1-3 | src={1}，tar={2,3} | `{1}` | `{2,3}` |
| 线 1-3、2-3 | src={1,2}，tar={3} | `{1,2}` | `{3}` |

> 验证要点：`roots` 最终**只含 `startId`**（虚拟开始节点挂接后），真实入口成为 `startId` 的 children。

### 3.3 循环区间推导

| 用例 | 结构 | 期望 `NodeLoopInfo.idsBetweenLoopEdge` |
| --- | --- | --- |
| 简单循环 | 循环线 A→B，中间节点 C | 含 A、B、C 及两端的内部连线 |
| 嵌套循环 | 外循环 A→D 内含内循环 B→C | 外循环区间含全部；内循环区间只含 B、C |

> 验证要点：区间 = 「source 的所有祖先」∩「target 的所有后代」+ 两端点。

### 3.4 强组合填充

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| 单节点入组 | `cells[0].groupIds = ["g1"]`，`groups = [{id:"g1", nodes:[]}]` | `groups[0].nodes = [cell.id]` |
| 多节点入组 | 两个节点 `groupIds` 均为 `["g1"]` | `groups[0].nodes` 含两个 id |

### 3.5 全局参数解析

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| 静态参数 | `staticParams: [{name:"a", type:"string", default:1}]` | `Inst.staticParams[0].key = "a"` |
| 动态参数 | `dynamicParams: [{name:"idx", type:"number", default:0}]` | `Inst.dynamicParams[0].value = 0` |
| 名称含空白 | `name: "  idx\t"` | 解析后被 `trim` 为 `"idx"` |

### 3.6 异常场景

| 用例 | 输入 | 当前行为 | 期望行为 |
| --- | --- | --- | --- |
| 缺开始节点 | 无 `node_start` | 抛 `NoSuchElementException` | 应抛业务异常并提示「缺少开始节点」 |
| 缺结束节点 | 无 `node_end` | 抛 `NoSuchElementException` | 应抛业务异常并提示「缺少结束节点」 |
| `cells` 为空 | `{}` | NPE | 应抛业务异常 |
| 非法 JSON | `"abc"` | 反序列化异常 | 应抛业务异常并提示「DSL 格式非法」 |

> 最后三行对应 [项目现状](10-项目现状.md) 缺陷 P3，属**待修复项**。

## §4 接口验证

### 4.1 算子注册三接口

**保存（`POST /registerOperator/save`）**

```bash
curl -X POST "http://localhost:8082/servicearrange/registerOperator/save" \
     -H "Content-Type: application/json" \
     -d '{
       "type": "http",
       "serviceName": "百度搜索",
       "serviceUrl": "www.baidu.com",
       "requestMethod": "post",
       "description": "测试登记",
       "reqBodyType": "json",
       "reqBodyIsJsonSchema": true,
       "resBodyType": "json",
       "resBodyIsJsonSchema": true
     }'
```

| 用例 | 期望 |
| --- | --- |
| 正常保存 | 返回 `"success"`；`REGISTER_INFO` 新增一条且 `createDate` 已填 |
| 带 `id` 保存 | 更新既有记录，`modifyDate` 刷新 |
| 缺 `serviceName` | 当前仍会保存成功（无必填校验）→ 建议补校验 |

**查询（`GET /registerOperator/findById?id=`）**

| 用例 | 期望 |
| --- | --- |
| id 存在 | 返回完整实体 JSON |
| id 不存在 | 返回 `null`（HTTP 200）|
| 不传 id | 依实现返回 `null` 或报错 |

**删除（`POST /registerOperator/delete`）**

```bash
curl -X POST "http://localhost:8082/servicearrange/registerOperator/delete" \
     -H "Content-Type: application/json" \
     -d '["6650f3a1c2b3d4e5f6a7b8c9"]'
```

| 用例 | 期望 |
| --- | --- |
| 删除存在的 id | 返回 `"success"`，记录消失 |
| 删除不存在的 id | 返回 `"success"`（幂等）|
| 传空数组 | 返回 `"success"` |

### 4.2 运行实例接口

```bash
# 运行
curl -X POST "http://localhost:8082/servicearrange/inst/run/or/getResult/PLAN_001" \
     -F "servea_optType=run" \
     -F "servea_sync=false" \
     -F "name=张三" \
     -F "age=28"

# 查询结果
curl -X POST "http://localhost:8082/servicearrange/inst/run/or/getResult/PLAN_001" \
     -F "servea_optType=get_result"
```

| 用例 | 期望 | 备注 |
| --- | --- | --- |
| `run` | 返回 `instId`；`SERVEA_INST` 新增文档，`state=RUNNING` | — |
| 请求头采集 | `Inst.headerParams` 含全部请求头 | 用 `-H "X-AToken: abc"` 验证 |
| 入参类型还原 | `age` 落库为数字 `28` 而非字符串 | 依赖 `inputsJsonSchema` |
| `get_result` 且成功 | 返回出参 | 需流程真正跑通 |
| `get_result` 且未成功 | HTTP 500 + `实例还未运行成功，无输出信息！` | 当前行为 |
| 查历史实例 | **不支持**，`servea_instId` 被忽略 | 缺陷 P2 |

### 4.3 前置条件

运行接口测试前必须：

1. 把目标 DSL 覆盖到 `backend/web/src/main/resources/hrh_http.json`；
2. 重启后端。

> 执行器与转换器已齐备，流程可完整跑通；若中途不推进，按 §6 与 [快速开始](11-快速开始.md) §5 的排查顺序处理。
> 也可以不走文件替换：把 DSL 通过 `POST /plan/save` 存为流程模型，再用其 `id` 作为 `planId` 运行。

## §6 缺陷复现与验证

原清单中的 5 项主链路缺陷已全部修复，保留复现与验证方法用于回归；MQ 真正投递仍为待办。

### 6.1 已修复缺陷的回归验证清单

| 编号 | 缺陷 | 修复位置 | 回归验证方法 |
| --- | --- | --- | --- |
| ✅ P0-1 | 决策线失效（`dicisionEdges` 恒为 `null`）| `TaskResultConsumer` 决策线处理段 | 表达式为真 → 目标节点正常执行；为假 → 目标节点置 `SKIP` |
| ✅ P0-2 | 转换器缺失（仅 start/end 两个 `TaskInterface`）| `convert/OperatorConverterConfig`（19 个 Bean）| 运行「开始 → 数据映射 → HTTP → 结束」，日志无 `getBean` 异常，各节点任务正常创建 |
| ✅ P1-1 | DSL 硬编码读 `hrh_http.json` | `InstController.loadDsl(planId)` | 两个不同 `planId` 执行不同流程；`DISABLED` 模型返回 400 |

### 6.8 错误码映射与重试分类（已落地能力）

| 项 | 内容 |
| --- | --- |
| 目的 | 确认 `task.error-mapping.*` 的三态分类真正影响重试走向，而非仅写字段 |
| 用例 ① | HTTP 节点返回 `503`（默认在 `retryable`）→ `errorClass=RETRYABLE`，实例日志出现「任务失败，第 N 次重试」 |
| 用例 ② | HTTP 节点返回 `404`（默认在 `fatal`）→ `errorClass=FATAL`，无重试日志，直接失败并按补偿线分支执行 |
| 用例 ③ | 返回 `200` 且 body 为 `{"code":"0"}` → `SUCCESS`（需配置 `body-code.path`）|
| 用例 ④ | 返回 `200` 且 body 为 `{"code":"PARAM_INVALID"}` → `FATAL`（业务码命中 `fatal` 列表）|
| 用例 ⑤ | 下游不可达触发连接超时 → `RETRYABLE`（命中 `retryable-exceptions` 的 `java.net.` 前缀）|
| 查询 | `db.SERVEA_TASK.find({instId:"..."},{nodeName:1,state:1,errorClass:1,errorCode:1,errorMessage:1})` |
| 兼容性 | 旧任务文档无 `errorClass` 字段时按可重试处理，行为与改造前一致，无需刷数据 |
