## §4 调度状态机

### 4.1 实例状态

```
        ┌──────────┐
        │  (创建)  │
        └────┬─────┘
             │ run
             ▼
        ┌──────────┐   全部节点完成    ┌──────────┐
        │ RUNNING  │─────────────────▶│ SUCCESS  │
        └────┬─────┘                  └──────────┘
             │ 任一节点 FAIL
             ├───────────────────────▶┌──────────┐
             │                        │   FAIL   │
             │ 人工挂起                └──────────┘
             ▼
        ┌──────────┐   恢复
        │ SUSPEND  │──────────▶ RUNNING
        └──────────┘
```

### 4.2 任务状态

```
   (创建) ──▶ RUNNING ──┬──▶ SUCCESS ──▶ 推进下一批节点
                        ├──▶ FAIL    ──▶ 有补偿线？→ 补偿任务 : 实例 FAIL
                        └──▶ SKIP    ──▶ 视为已处理，继续推进
```

`SKIP` 的三种产生场景：

| 场景 | 说明 |
| --- | --- |
| 父节点全部 SKIP | 子节点也被跳过（`TaskResultConsumer` L388-393）|
| 决策线不通过 | 目标节点被置 SKIP，流程改走其他分支（L396-415）|
| 循环区间重置 | 区间内节点在每轮循环开始时被移出状态集合（L215-222）|

## §6 关键缺陷清单

按严重程度排序（**本次不修复后端**，仅记录以便后续排期）：

| 严重度 | 位置 | 问题 | 影响 |
| --- | --- | --- | --- |
| **P0** | `TaskResultConsumer` L381-385 | `inputEdges.stream()...collect(...)` 结果**未接收**，`dicisionEdges` 恒为 `null` | 决策线判断永不生效，条件分支功能完全不可用 |
| **P0** | `TaskResultConsumer` L334 | whileDo 分支使用 `outLoopEdges.get(0)`，而该分支内 `outLoopEdges` 可能为 `null` | whileDo 循环触发 NPE |
| **P1** | 24 种类型仅 2 个 `TaskInterface` 实现 | 非 start/end 节点无转换器 | `SpringUtil.getBean(..., "_task")` 失败，多数节点无法转任务 |
| **P1** | 24 种类型仅 4 个 `Execute` 实现 | 非 start/end/datamap/http 节点无执行器 | `SpringBeanUtils.getBean(task.getType())` 返回 null，补偿/Dubbo/脚本等全部不可用 |
| **P1** | `InstController#run` L80 | DSL 硬编码 `FileUtil.readUtf8String("hrh_http.json")` | 无法按 `planId` 运行不同流程 |
| P2 | `InstController` L178-189 | `get_result` 分支不使用 `servea_instId`，只查本次新建实例 | 无法查询历史实例结果 |
| P2 | `InstController` L210-229 | 文件下载分支 `fileName` 可能为 `null` 即 `URLEncoder.encode` | 非 JSON 出参场景 NPE |
| P2 | `TaskResultConsumer` L389 | `pSkipNum == skipNodes.size()` 语义应为 `pids.size()` | SKIP 传播判断可能失效 |
| P2 | `TaskProductor` L42/L49 | 名为「生产」实为本地直调 | 多实例部署时任务不会分发到其他节点 |
| P3 | `DataMapOperateExecutor` L283 | `jsonObject.equals(expression)` 疑似应为 `containsKey` | 上游节点取值分支可能失效 |
| P3 | `DslParser` L261/L278 | `static` 计数器 `Chilednum`/`Parentnum` 做递归出口 | 并发解析时结果错误 |
| P3 | `DslParser` L33/L139/L152 | `Optional.get()` 未判空 | DSL 缺首尾节点时抛 `NoSuchElementException` |
| P3 | `TaskType` L25-47 | 除 start/end 外常量被整体注释 | 可读性差，靠约定易出错 |
| P3 | `HttpTaskExecutor` L140-147 | 文件下载注释为 TODO，`fileList` 恒为空 | 文件上传功能不可用 |

## §7 后续迭代建议

按优先级排列：

1. **修复决策线与 whileDo 的 Bug**（高优先，否则条件分支/循环能力不可用）；
2. **补齐 `Plan` 模型管理**：新增 `Plan` 实体、Mongo 集合与 CRUD 接口，让 `planId` 真正关联 DSL；
3. **实现脚本类算子**（Shell / Jar / Python）：复用 `FUN_SHELL` 执行器，落地进程管理与超时控制；
4. **补齐 Dubbo / WebService 算子**及其补偿算子；
5. **把 `TaskProductor` 改为真正的 MQ 投递**，启用 `MqChannelProcessor` 中已定义的通道，支持多实例水平扩容；
6. **完善 `DslParser` 的健壮性**：递归计数器改为方法参数传递、`Optional` 判空并给出明确错误信息；
7. **补齐实例列表 / 详情 / 执行轨迹接口**，前端即可实现运行监控与历史回放；
8. **统一异常处理与接口返回结构**（`{code,msg,data}`），前端已按此契约预留。
