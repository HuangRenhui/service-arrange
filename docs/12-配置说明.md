#### 3.3.3 错误码映射与重试策略配置（`task.error-mapping.*`）

> ✅ **已落地（2026-10-22）**。配置由 `config/ErrorMappingProperties` 承载，
> `executor/ErrorClassifier` 产出三态分类，各协议执行器写入 `Task.errorClass`，
> `TaskResultConsumer` 据此决定是否进入重试。
> 设计目的：换协议 / 换厂商时**只改映射配置，调用方（编排、重试、补偿）零改动**，回滚也只需回退一行配置。

**改造前的硬编码判定（已替换，保留作对照）**：

| 执行器 | 当前判定 |
| --- | --- |
| `HttpTaskExecutor` | `status != 200` 即失败（另有一个 `error` 字段包含判断）|
| `WebServiceOperateExecutor` / `DubboOperateExecutor` | `2xx = SUCCESS`，SOAP Fault / 泛化错误码不可区分 |
| `SqlOperateExecutor` | 抛异常即 `FAIL`，无法区分死锁（可重试）与语法错误（重试无意义）|
| `ScriptOperateExecutor` | `exitCode == 0`，退出码语义不可配置 |

**三态分类（已实现）**

| 分类 | 语义 | 与现有机制的衔接 |
| --- | --- | --- |
| `SUCCESS` | 调用成功 | 维持现有成功路径 |
| `RETRYABLE` | 可重试错误（限流、网关 5xx、死锁、串行化失败）| 走既有 `Task.RetryRules`（`times` / `doneTimes` / `delaySecondTimes`，受 `task.orchestration.retry-delay-max-ms` 封顶）|
| `FATAL` | 不可重试错误（参数、权限、业务拒绝）| **跳过重试**，直接置 `FAIL` 并触发 `edge_compensate` 补偿分支，不空等重试次数 |

**两级配置**（与现有「全局 yml + 节点 DSL」双层设计同构）：

| 层 | 位置 | 状态 | 换协议时的动作 | 回滚 |
| --- | --- | --- | --- | --- |
| 全局默认 | `application.yml`（`task.error-mapping.*`）| ✅ 已实现 | 改一段 yml，执行器零改动 | `git revert` 一行 |
| 算子级覆盖 | 节点 `data.errorMapping`（随 `JsonPayloadTask` 整包写入 `Task.inputs`）| ✅ 已实现 | 只改该节点 DSL，其他节点与全局不受影响 | 重新发布旧版 `Plan` 即回滚 |

**配置结构（`application.yml`，已落地默认值）**：

```yaml
task:
  error-mapping:
    # 未知错误码的默认分类：conservative(→FATAL) / optimistic(→RETRYABLE)
    default-action: conservative
    # 无错误码场景下按可重试处理的异常类名前缀（连接超时、连接重置、瞬时 SQL 异常）
    retryable-exceptions:
      - java.net.
      - java.io.IOException
      - java.util.concurrent.TimeoutException
      - java.sql.SQLTransientException
    protocols:
      http:
        match: status                 # status | body-jsonpath | soap-fault | sqlstate | exit-code
        success: [200, 204]
        retryable: [429, 502, 503, 504]
        fatal: [400, 401, 403, 404, 422]
        body-code:                    # HTTP 2xx 但业务码非 0 的主流厂商形态，不配则只看状态码
          path: $.code
          success: ["0"]
          retryable: ["SYS_BUSY", "LOCKED"]
          fatal: ["PARAM_INVALID", "NO_PERMISSION"]
      dubbo:
        match: body-jsonpath
        path: $.errorCode             # 取不到业务码时回退 HTTP 状态码
        success: ["0"]
        retryable: []
        fatal: []
      webservice:
        match: soap-fault
        retryable: ["Server.Timeout"]
        fatal: ["Client.Validation"]
      sql:
        match: sqlstate
        retryable: ["40001", "40P01"]
        fatal: ["42xxx", "07xxx"]
      script:
        match: exit-code
        success: ["0"]
        retryable: []
        fatal: []
```

> 通配规则：错误码列表支持 `42xxx` / `42*` 前缀匹配，其余按忽略大小写全等。
> `default-action` 只影响**未命中任何列表、且异常前缀也未匹配**的错误码。

**算子级覆盖（节点 `data.errorMapping`）**：

与单个协议的规则同构，直接写在节点 `data` 里，优先级高于全局：

```json
{
  "url": "http://api.example.com/pay",
  "requestType": "POST",
  "errorMapping": {
    "retryable": [502, 503, 504],
    "fatal": [400, 401, 403],
    "bodyCode": {
      "path": "$.code",
      "success": ["0"],
      "retryable": ["SYS_BUSY"],
      "fatal": ["PARAM_INVALID", "NO_PERMISSION"]
    }
  }
}
```

> 合并语义为「节点表优先、全局表兜底」：节点只声明差异码即可，未声明的码继续按全局规则判定；
> `match` / `path` 未写时沿用全局。`errorMapping` 缺失或 JSON 非法时静默回退全局，不影响流程执行。
> 该字段随节点 `data` 整包持久化，无需前端表单支持，通过 DSL 导入 / 导出即生效。

**实现位置（已落地）**：

| 位置 | 实现要点 |
| --- | --- |
| `config/ErrorMappingProperties.java` | `@ConfigurationProperties(prefix = "task.error-mapping")`，含 `defaultAction`、`retryableExceptions`、`protocols` |
| `executor/ErrorClass.java` | 三态枚举 `SUCCESS` / `RETRYABLE` / `FATAL` |
| `executor/ErrorClassifier.java` | 输入协议 + status/响应体/异常 → 三态 + 归一化 code/message；支持 jsonpath、SOAP Fault、SQLState（沿异常链）、退出码、通配与异常前缀兜底；节点 `errorMapping` 按「节点表优先、全局表兜底」两层判定 |
| `entity/Task.java` | 新增 `errorClass` / `errorCode` / `errorMessage` 三个持久化字段 |
| 5 个执行器 | `HttpTaskExecutor`、`DubboOperateExecutor`、`WebServiceOperateExecutor`、`SqlOperateExecutor`、`ScriptOperateExecutor` 的硬编码判定替换为分类调用；配置缺失类错误直接判 `FATAL` |
| `executor/Execute.java` | 结果投递前 `taskDao.save(task)`，保证分类字段落库；执行超时判 `RETRYABLE`，框架异常走分类兜底 |
| `mq/TaskResultConsumer.java` | 仅 `RETRYABLE` 进入重试；`FATAL` 记 WARN 日志后直接失败并触发补偿；`errorClass` 为 null 的旧数据按可重试处理 |

**两个设计要点**：

1. 取错误码必须支持 **jsonpath**（`body-code.path`），否则「HTTP 200 + body `code≠0`」这种主流形态仍要改代码；
2. 未知错误码的默认分类按**副作用**决定：查询类可乐观重试，扣款 / 下单类建议保守（直接失败转补偿或人工）。

以下配置项由业务代码通过 `@Value` 注入，是**必须存在**的属性。

| 配置项 | 值（当前） | 注入位置 | 说明 |

**ZooKeeper 用途说明**：实例级分布式锁，路径为 `/INST_LOCK_{instId}`，节点类型 `CreateMode.EPHEMERAL`。同一实例的任务结果消息严格串行处理，避免状态集合并发推进。会话断开时临时节点自动删除，天然防死锁。详见 [数据模型与消息模型](04-数据模型与消息模型.md) §11。

**队列名用途说明**：`task.run_queue_name` / `task.result_queue_name` 同时被用作：

1. `TaskProductor` 中的 `@Value` 注入；
2. `application.yml` 中两个 input channel 的 `group` 与 `binding-routing-key`。

两处必须保持一致，否则消息路由错乱。

## §5 外部化配置

### 5.1 Apollo 配置中心

**已移除**。原 `apollo-client` 依赖、`META-INF/app.properties`、`application*.yml` 中的 `apollo.*` 配置段均已删除。

移除原因：`apollo-client` 的 `META-INF/spring.factories` 注册了 `ApolloApplicationContextInitializer`，Spring 启动时会强制实例化它；而 `apollo.bootstrap.enabled=false` 只对 `apollo-spring-boot-starter` 生效，拦不住该初始化器，导致启动即抛：

```
IllegalArgumentException: Cannot instantiate interface
  org.springframework.context.ApplicationContextInitializer :
  com.ctrip.framework.apollo.spring.boot.ApolloApplicationContextInitializer
```

后续如需接入 Apollo，应改用配套 starter 并补齐传递依赖。

### 5.2 Eureka 服务注册

**已移除**。原 `spring-cloud-starter-netflix-eureka-client` 依赖、`@EnableEurekaClient` 注解、`application*.yml` 中的 `eureka.*` 配置段，以及父 pom 的 `eureka.version` / `eureka-url` 属性均已删除。

当前服务以**独立方式运行**，不依赖任何注册中心。

按优先级排列。

| 优先级 | 项 | 现状 | 建议 |

      database: servicearrange
      username: ${MONGO_USERNAME}
      password: ${MONGO_PASSWORD}
  cloud:
    stream:
      binders:
        rabbit_cluster:
          type: rabbit
          environment:
            spring:
              rabbitmq:
                addresses: ${MQ_ADDRESSES}
                username: ${MQ_USERNAME}
                password: ${MQ_PASSWORD}

zk:
  url: ${ZK_URL}
  session-timeout: 5000

task:
  run_queue_name: /task/run
  result_queue_name: /task/result
```

export MONGO_HOST=10.0.0.11 MONGO_USERNAME=app MONGO_PASSWORD='***'
export MQ_ADDRESSES=10.0.0.12:5672 MQ_USERNAME=app MQ_PASSWORD='***'
export ZK_URL=10.0.0.13:2181
java -jar service-arrange.jar
```
