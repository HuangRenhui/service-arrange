## §1 命名约定

### 1.1 核心约定：Bean 名即契约（强制）

这是本项目**最重要的一条规范**。引擎通过 Bean 名做依赖查找，因此命名即接口。

| 组件 | Bean 名 | 查找位置 |
| --- | --- | --- |
| `Execute` 执行器 | `cellType` | `TaskRunConsumer` L68-72 |
| `TaskInterface` 转换器 | `cellType + "_task"` | `TaskResultConsumer` L177 / L243 / L365 |

示例：

```java
// 执行器：Bean 名 = cellType
@Service(CellType.OPERATOR_HTTP)              // "node_outer_http"
public class HttpTaskExecutor implements Execute { }

// 转换器：Bean 名 = cellType + "_task"
@Service(CellType.OPERATOR_HTTP + TaskType.suffix)   // "node_outer_http_task"
public class HttpTask implements TaskInterface { }
```

> ❌ **禁止**在 `@Service` 中写硬编码字符串（如 `@Service("httpExecutor")`），必须用 `CellType` 常量拼接。
> ❌ **禁止**在 `TaskResultConsumer` 中写 `if (cellType.equals("xxx"))` 这类类型判断分支。

### 1.2 `cellType` 命名规范（强制）

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `node_start` / `node_end` | 首尾节点（各仅一个）| 固定 |
| `node_inner_` | 内部算子（无外部依赖）| `node_inner_datamap` |
| `node_outer_` | 外部服务调用 | `node_outer_http` |
| `node_outer_xxxCompensate` | 补偿算子 | `node_outer_httpCompensate` |
| `edge_` | 连线 | `edge_decision` |
| `group_` | 强组合 | `group_compensate` |
| `global_Data` | 全局参数（历史遗留大写）| 固定 |

命名风格：**小写 + 下划线分隔 + 驼峰混合**（如 `node_inner_transform2Obj`）。新增时请遵循现有风格，勿自创。

### 1.3 Java 命名

| 元素 | 规范 | 示例 |
| --- | --- | --- |
| 类 | 大驼峰 | `DataMapOperateExecutor` |
| 接口 | 大驼峰（业务接口加 `I` 前缀）| `Execute` / `ITaskService` |
| 方法 | 小驼峰，动词开头 | `runProcess` / `edgeDecisionDo` |
| 常量 | 全大写下划线 | `STATE_RUNNING` / `ZK_LOCK_PREFIX` |
| 成员变量 | 小驼峰 | `loopRunTimesMap` |
| 包 | 全小写 | `com.hrh.servicearrange.parser` |

**类型后缀约定**：

| 后缀 | 用途 |
| --- | --- |
| `Cell` | DSL 节点数据结构 |
| `Executor` | 算子执行器 |
| `Task` | Cell → Task 转换器 |
| `Dao` | Mongo 数据访问接口 |
| `Service` / `ServiceImpl` | 业务服务接口与实现 |
| `Controller` | Web 接口 |
| `Vo` | 入参/出参对象 |
| `Entity` | 持久化实体 |
| `Config` | 配置类 |

### 1.4 命名避坑（反面案例）

以下为仓库中**已存在的错误命名**，新增代码请勿模仿，修复时注意兼容：

| 错误命名 | 应为 | 位置 |
| --- | --- | --- |
| `starDate` | `startDate` | `Inst` |
| `LEVEL_ERRO` | `LEVEL_ERROR` | `InstLog` |
| `sheelFtpPath` | `shellFtpPath` | `RegisterInfoEntity` |
| `dicisionEdges` | `decisionEdges` | `TaskResultConsumer` |
| `nAckTask` | `nackTask` | `TaskProductor` |

## §2 分层职责

### 2.1 依赖方向（强制）

```
controller  →  service  →  dao  →  entity
     ↓            ↓
    vo          utils
     
executor  →  service / dao / mq
convert   →  dsl / entity
parser    →  dsl / entity
mq        →  service / dao
```

**禁止反向依赖**：`dao` 不得依赖 `service`；`entity` 不得依赖任何业务包；`dsl` 包保持纯净（不依赖 Spring）。

### 2.2 各层职责边界

| 层 | 应做 | 不应做 |
| --- | --- | --- |
| `controller` | 参数校验、类型还原、调用 service、组装响应 | 写业务逻辑、直接访问 dao |
| `service` | 业务规则、表达式求值、事务边界 | 处理 HTTP 细节 |
| `dao` | 数据访问，仅继承接口方法 | 写业务判断 |
| `parser` | DSL → 图结构 | 执行流程、访问 MQ |
| `convert` | Cell → Task 转换 | 执行算子 |
| `executor` | 单节点执行逻辑 | 调度决策（下一节点由 `mq` 层决定）|
| `mq` | 消息收发、状态推进、调度决策 | 具体算子实现 |
| `dsl` | 纯数据结构 | 任何 Spring 注解、业务方法 |

### 2.3 执行器实现规范（强制）

`Execute.runProcess` 是唯一需要重写的抽象方法，实现时必须遵守四条：

```java
@Service(CellType.XXX)
public class XxxExecutor implements Execute {

    @Override
    public Task runProcess(Task task, Inst inst, TaskDao taskDao, InstLogDao instLogDao) {
        // ① 记录开始时间
        task.setExecutorStartDate(new Date());
        try {
            // ② 执行核心逻辑
            // ③ 组装出参到 task.setOutputs(...)
            task.setState(Task.STATE_SUCCESS);
        } catch (Exception e) {
            // ④ 异常必须转为 FAIL，不要向上抛
            task.setState(Task.STATE_FAIL);
            instLogDao.save(new InstLog(task.getInstId(), task.getPlanId(),
                    task.getNodeId(), task.getId(), InstLog.LEVEL_ERRO, e.getMessage()));
        }
        task.setExecutorEndDate(new Date());
        return task;
    }
}
```

| # | 规则 | 原因 |
| --- | --- | --- |
| 1 | 必设 `executorStartDate` / `executorEndDate` | 用于耗时统计 |
| 2 | 出参写入 `task.setOutputs()`，不要直接改 `inst` | 保持数据流单向 |
| 3 | **异常必须捕获并置 `FAIL`** | 直接抛出会触发 MQ `nack` 重试，5 次后强制 ack 且流程滞留 |
| 4 | **不要自己调用 `sendTaskResult`** | 由 `Execute.run()` 模板方法统一调用（L44）|

> ⚠️ 违反第 4 条会导致结果重复回传；遗漏调用（若绕过模板方法）会导致流程永久卡住。

### 2.4 转换器实现规范（强制）

⚠️ **实现 `process`，不要重写 `convert`**。`convert(cell, inst)` 是框架的 `default` 模板方法，已自动装配全部公共字段（含 `loopTimes` 推导）。

```java
@Service(CellType.XXX + TaskType.suffix)
public class XxxTask implements TaskInterface {

    @Override
    public Task process(Cell cell, Inst inst, Task task) {
        // 公共字段（instId / planId / nodeId / nodeName / type / state / loopTimes）
        // 均已在 convert 模板方法中装配完毕，此处只需处理业务入参
        XxxCell c = JSONUtil.toBean(JSONUtil.parseObj(cell), XxxCell.class);
        task.setInputs(...);
        return task;
    }
}
```

| # | 规则 | 原因 |
| --- | --- | --- |
| 1 | **只实现 `process`**，不重写 `convert` | 重写会丢失公共字段装配 |
| 2 | 尤其不能丢 `loopTimes` | 否则同一节点的不同循环轮次任务会互相覆盖 |
| 3 | 子类**不应**自行设置 `type` / `state` | `convert` 已设为 `cellType` / `STATE_WAITE` |
| 4 | 若确需重写 `convert`，必须 `return TaskInterface.super.convert(cell, inst)` 或完整复刻其逻辑 | 保持与引擎一致 |

**`loopTimes` 推导规则**（由 `convert` 自动完成，L35-42）：取覆盖该节点的**所有循环线中区间最小的那条**（即最近一层循环），格式为 `循环线id|次数`；不在任何循环区间内则为 `"0"`。

## §3 注释规范

### 3.1 类注释（强制）

每个类必须有类注释，说明用途；Spring Bean 需标注对应的 `cellType`。

```java
/**
 * HTTP 调用算子执行器。
 * <p>对应 cellType：{@link CellType#OPERATOR_HTTP}（node_outer_http）</p>
 * <p>支持 GET/POST/PUT；状态码非 200 或响应含 error 关键字时判定失败。</p>
 */
@Service(CellType.OPERATOR_HTTP)
public class HttpTaskExecutor implements Execute { }
```

### 3.2 方法注释（强制）

公开方法必须有注释，说明**做什么**与**为什么**，而非重复签名。

```java
/**
 * 推导节点所在的循环标识。
 *
 * @param cell 目标节点
 * @param inst 实例（含 loopRunTimesMap）
 * @return 循环标识，格式 {@code 循环线id|次数}；不在循环内返回 {@code "0"}
 */
```

### 3.3 行内注释

只在**逻辑不直观处**写注释，解释「为什么」而非「是什么」。

```java
// 好：解释原因
// 循环线不代表实际流转，参与入出度计算会导致真实入口推导错误
List<EdgeCommonCell> edges = cells.stream().filter(c -> !EDGE_LOOP.equals(c.getCellType()))...

// 坏：复述代码
// 遍历所有 cells
for (Cell cell : cells) { }
```

### 3.4 禁止的注释形式

| 禁止 | 原因 |
| --- | --- |
| 大段被注释掉的代码 | 用 Git 管理历史，勿留在源码中（`TaskType` 中已有此类问题）|
| `TODO` 无责任人 | 必须写成 `// TODO(姓名, 日期): 说明`，或建 Issue |
| 空注释块 `/** */` | 无信息量 |
| 注释与代码不一致 | 改代码必须同步改注释 |

## §4 异常处理

### 4.1 当前问题

项目**没有**全局异常处理器（无 `@ControllerAdvice`），异常直接抛出，导致：

- 接口返回 HTTP 500 错误页而非结构化 JSON；
- 前端需要特判响应类型；
- 敏感堆栈信息可能外泄。

### 4.2 规范要求

| # | 规则 |
| --- | --- |
| 1 | 业务异常统一使用 `BizException`（建议新增），携带错误码与用户可读消息 |
| 2 | 禁止 `catch (Exception e) { }` 静默吞异常 |
| 3 | 禁止用异常做流程控制 |
| 4 | 执行器内部异常必须转为 `Task.STATE_FAIL`，不向上抛（见 §2.3 规则 3）|
| 5 | `Optional` 取值为空时给出明确业务提示，禁止裸 `get()` |
| 6 | 新增 `@ControllerAdvice` 统一转换为 `{code, msg, data}` |

### 4.3 反面案例（仓库现存）

| 位置 | 问题 |
| --- | --- |
| `DslParser` L33 / L139 / L152 | `Optional.get()` 未判空 → 抛 `NoSuchElementException`，错误信息不友好 |
| `InstController` L210-229 | `fileName` 可能为 `null` 即 `URLEncoder.encode` → NPE |
| `TaskResultConsumer` L334 | `outLoopEdges` 可能为 `null` 即 `.get(0)` → NPE |

### 4.4 推荐写法

```java
// 判空并给出业务提示
Cell startCell = cells.stream()
        .filter(c -> CellType.START.equals(c.getCellType()))
        .findFirst()
        .orElseThrow(() -> new BizException("DSL 非法：缺少开始节点 node_start"));

// 集合访问前判空
if (CollectionUtil.isEmpty(outLoopEdges)) {
    return task;
}
EdgeLoopCell loopEdge = (EdgeLoopCell) outLoopEdges.get(0);
```

## §5 日志规范

### 5.1 两类日志

| 类型 | 用途 | 输出位置 |
| --- | --- | --- |
| 系统日志 | 开发排查、异常堆栈 | `slf4j` → 控制台/文件 |
| 业务日志 | 流程执行轨迹（面向使用者）| `InstLog` 集合 |

**两者不可混用**：用户能看到的流程轨迹写入 `InstLog`；技术异常写系统日志（同时可落一条 `LEVEL_ERRO` 的 `InstLog`）。

### 5.2 `InstLog` 使用规范

```java
// 5 参构造：默认 INFO 级别
instLogDao.save(new InstLog(task.getInstId(), task.getPlanId(),
        task.getNodeId(), task.getId(),
        task.getNodeName() + "节点开始执行....."));

// 6 参构造：指定级别
instLogDao.save(new InstLog(task.getInstId(), task.getPlanId(),
        task.getNodeId(), task.getId(),
        InstLog.LEVEL_ERRO, "下标越界！" + e.getMessage()));
```

| 规则 | 说明 |
| --- | --- |
| 必须传 `instId` / `planId` / `nodeId` / `taskId` | 四个维度是查询过滤的基础 |
| 内容以 `节点名 + 动作` 开头 | 便于人工阅读 |
| 关键节点记录「开始 / 成功 / 失败 / 异常」四态 | 参考 `HttpTaskExecutor` |
| 避免记录密钥、密码、完整请求体 | 防敏感信息泄漏 |

### 5.3 级别使用

| 级别 | 场景 |
| --- | --- |
| `LEVEL_INFO` | 节点开始/成功、状态推进 |
| `LEVEL_WARN` | 可恢复问题：越界、重试、跳过 |
| `LEVEL_ERRO` | 节点失败、异常 |

## §6 前端规范

### 6.1 基本约束

| 约束 | 说明 |
| --- | --- |
| 零依赖 | 不引入任何第三方库，不用构建工具 |
| ES5 语法 | 使用 `var` / `function`，不使用 `let` / `const` / 箭头函数 / 模板字符串 |
| IIFE 模块化 | 每个文件用 `(function (global) { ... })(window);` 包裹 |
| 全局命名空间 | 只挂载一个全局对象，避免污染 |

### 6.2 模块模板

```javascript
/* ===== 模块说明 ===== */
(function (global) {
  'use strict';

  var MyModule = {
    init: function () { /* ... */ }
  };

  global.MyModule = MyModule;
})(window);
```

### 6.3 命名与风格

| 元素 | 规范 | 示例 |
| --- | --- | --- |
| 全局对象 | 大驼峰 | `DslValidator` / `NodeDefs` |
| 对象方法 | 小驼峰 | `validate` / `renderNodes` |
| 私有函数 | 小驼峰，文件内定义 | `function esc(s)` |
| CSS 类 | 小写 + 中划线 | `.node-port` / `.edge-path` |
| DOM id | 小驼峰 | `nodesLayer` / `btnExport` |

### 6.4 新增节点类型（前端侧）

在 `js/nodes.js` 的 `NODES` 数组追加一项，字段必须齐全：

```javascript
{
  cellType: 'node_inner_xxx',      // 必填，与后端 CellType 完全一致
  name: '显示名',                   // 必填，节点库与默认节点名
  cat: 'inner',                    // 必填，分类 key（basic/edge/inner/script/outer/compensate）
  kind: 'node',                    // 必填，'node' 或 'edge'
  icon: '×',                       // 建议，简短标识
  desc: '一句话说明',                // 建议，tooltip
  defaultData: function () { return {}; },   // 必填，新建时的 data 模板
  schema: [                        // 属性面板字段定义
    { key: 'fieldName', label: '标签', type: 'text', hint: '提示' }
  ]
}
```

支持的字段类型：`text` / `textarea` / `number` / `select` / `json` / `strlist` / `kv` / `kvpath` / `rules`。

### 6.5 安全规范

| # | 规则 | 原因 |
| --- | --- | --- |
| 1 | 所有插入 DOM 的用户输入必须经 `esc()` 转义 | 防 XSS |
| 2 | 禁止 `innerHTML` 直接拼接未转义的变量 | 同上 |
| 3 | 不在前端存储敏感信息 | localStorage 可被读取 |
| 4 | 接口地址可配置，不硬编码 | 便于多环境部署 |

## §7 提交流程

### 7.1 分支策略

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定分支，可发布 |
| `feature/xxx` | 特性开发 |
| `fix/xxx` | 缺陷修复 |
| `docs/xxx` | 文档完善 |

### 7.2 提交信息规范

采用 **Conventional Commits**：

```
<type>(<scope>): <subject>

<body>

<footer>
```

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `refactor` | 重构（不改行为）|
| `perf` | 性能优化 |
| `test` | 测试 |
| `chore` | 构建/工具 |

示例：

```
feat(executor): 实现 Shell 算子执行器

- 新增 ShellTaskExecutor，Bean 名 node_inner_execShell
- Jar/Python 复用该执行器（TaskRunConsumer 路由已支持）
- 补充超时控制与输出采集

Refs: docs/09-功能清单.md §C
```

### 7.3 提交前自检

**后端**

- [ ] 新增 Bean 名符合 `cellType` / `cellType + "_task"` 约定
- [ ] 未在引擎中新增 `if (cellType == "xxx")` 类型分支
- [ ] 执行器内部异常已转为 `Task.STATE_FAIL`
- [ ] 未自行调用 `sendTaskResult`
- [ ] 未新增硬编码的密码/地址
- [ ] `mvn clean compile` 通过

**前端**

- [ ] 新增节点已在 `js/nodes.js` 登记
- [ ] 所有用户输入已 `esc()` 转义
- [ ] 未引入第三方库
- [ ] 保持 ES5 语法
- [ ] `node --check` 通过
- [ ] 新增/修改的 DOM id 在 JS 与 HTML 中双向一致

**文档**

- [ ] 按 [文档说明](文档说明.md) 「维护」章节同步对应文档
- [ ] 文档修订记录只写入 [文档说明](文档说明.md) 的「修订」章节

### 7.4 代码评审关注点

| # | 关注点 |
| --- | --- |
| 1 | Bean 命名是否符合契约（这是最容易出错也最致命的一点）|
| 2 | `loopTimes` 推导是否与引擎一致 |
| 3 | 异常是否被正确捕获并置 FAIL |
| 4 | 是否存在 NPE 风险（集合判空、`Optional.get()`）|
| 5 | 是否引入了循环依赖 |
| 6 | 新增配置项是否已补充到 `application.yml` 并写入 [配置说明](12-配置说明.md) |
| 7 | 前端是否对新增节点做了 DSL 校验兼容 |
