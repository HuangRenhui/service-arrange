## §1 扩展点全览

新增一个节点类型，需要对齐 5 个扩展点：

| # | 扩展点 | 位置 | 作用 |
| --- | --- | --- | --- |
| 1 | `CellType` 常量 | `parser/annotation/CellType.java` | 定义 `cellType` 字面值 |
| 2 | `Cell` 子类 | `dsl/` 包 | 定义该节点的 `data` 结构 |
| 3 | `TaskInterface` 实现 | `convert/` 包 | Cell → Task 转换，Bean 名 = `cellType + "_task"` |
| 4 | `Execute` 实现 | `executor/impl/` 包 | 实际执行逻辑，Bean 名 = `cellType` |
| 5 | 前端节点定义 | `frontend/` | 画布渲染 + 属性面板 |

其中 ①②③④ 属后端（本次不实现），⑤ 属前端（本次已按契约预留）。

---

## §2 命名约定（强约束）

```
cellType      = "node_inner_xxx"     ← 节点；"edge_xxx" ← 连线
Execute Bean  = cellType             ← 执行器按 type 直取
TaskInterface = cellType + "_task"   ← 转换器，TaskType.suffix = "_task"
```

**这两个 Bean 名是引擎的硬约定**：

- `TaskRunConsumer` L68-71：`SpringBeanUtils.getBean(task.getType())` 取执行器；
- `TaskResultConsumer` L177/L243/L365：`SpringUtil.getBean(cell.getCellType() + TaskType.suffix)` 取转换器。

只要 Bean 名符合约定，**无需修改引擎任何调度代码**，节点即被自动接入。

## §3 步骤详解

### 步骤 1：定义 `cellType`

在 `CellType` 中新增常量，例如：

```java
/** 邮件发送 */
public static final String FUN_EMAIL = "node_inner_sendEmail";
```

命名建议：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `node_start` / `node_end` | 首尾节点 | 固定两个 |
| `node_inner_` | 内部算子（无外部依赖）| `node_inner_datamap` |
| `node_outer_` | 外部服务调用 | `node_outer_http` |
| `node_outer_xxxCompensate` | 补偿算子 | `node_outer_httpCompensate` |
| `edge_` | 连线 | `edge_decision` |
| `group_` | 强组合 | `group_compensate` |

### 步骤 2：定义 Cell 与 data 结构

在 `dsl/` 包新增 `FunEmailCell extends Cell`，内部类 `Data` 描述属性面板字段。**必须提供无参构造与 getter/setter**（Hutool `JSONUtil.toBean` 依赖）。

参照现有实现：

| 现有 Cell | 参考点 |
| --- | --- |
| `FunDatamapCell` | 多组键值对 + `KeyValueWithJsonPathDto`（含 `jsonpathMapping`）|
| `FunTransform2ObjCell` | 规则列表 `TransformRule`（`key` / `keyType` / `type` / `jsonpathMapping` / `defaultValue`）|
| `EdgeDecisionCell` | 条件列表 `ConditionData` + `R[]` / `L[]` / `jsonpathElexpression` |

**取值表达式约定**：凡涉及取值的字段统一用字符串承载表达式，语法见 [02-DSL规范 §4.3](02-DSL规范.md)：

```
#节点id$jsonpath
#pno_节点id$jsonpath
#header_$HeaderName
#dynamicParams_$idx
#start_$field
```

### 步骤 3：实现 `TaskInterface`

⚠️ 注意实现的是 **`process`**（抽象方法），**不要**重写 `convert`（框架模板方法，已负责公共字段装配）。

```java
@Service(CellType.FUN_EMAIL + TaskType.suffix)   // → "node_inner_sendEmail_task"
public class FunEmailTask implements TaskInterface {
    @Override
    public Task process(Cell cell, Inst inst, Task task) {
        // 1. 反序列化 data：JSONUtil.toBean(JSONUtil.parseObj(cell),
        //                                 FunEmailCell.class).getData()
        // 2. 组装入参 → task.setInputs(...)（可复用 DataMapOperateExecutor 的映射能力）
        // 3. 只需处理业务入参；公共字段由 convert 模板方法已装配完毕
        return task;
    }
}
```

**关键点**：

- **只实现 `process`**。`convert(cell, inst)` 是 `default` 模板方法，已自动装配 `instId` / `planId` / `nodeId` / `nodeName` / `type` / `state=WAITE` 与 **`loopTimes`**；
- 若手工重写 `convert`，会丢失 `loopTimes` 推导 → 同一节点不同循环轮次的任务互相覆盖；
- `nodeName` 回退逻辑（`cellType + "_" + id`）与 `loopTimes` 推导（取**区间最小**的循环线，即最近一层循环）均在 `convert` 内完成，无需重复。

参考已有实现：`StartTask`（写 `outputs.value` / `jsonSchema` / `headerParams`）、`EndTask`（把节点 data 放进 `inputs`）。

### 步骤 4：实现 `Execute`

⚠️ 注意实现的是 **`runProcess`**（抽象方法），**不要**重写 `run`（框架模板方法）。

```java
@Service(CellType.FUN_EMAIL)
public class EmailTaskExecutor implements Execute {
    @Override
    public Task runProcess(Task task, Inst inst, TaskDao taskDao, InstLogDao instLogDao) {
        // 1. 执行（发邮件）
        // 2. 回写 task.setOutputs(...) 与 task.setState(STATE_SUCCESS)
        // 3. 异常时 task.setState(STATE_FAIL)，不要向上抛
        return task;
    }
}
```

**关键点**：

- **只实现 `runProcess`**。`run(tid)` 是 `default` 模板方法，已负责：查任务 → 置 `RUNNING` → 记录 `executorStartDate` → 调用 `runProcess` → 状态归一（非 `FAIL` 一律置 `SUCCESS`）→ 调用 `sendTaskResult`；
- **不要在 `runProcess` 中调用 `sendTaskResult`**，否则结果会重复回传；
- 失败时 `task.setState(Task.STATE_FAIL)`，编排层会自动判断是否走补偿分支；
- 异常应尽量捕获并转为 `FAIL` 状态，不要直接向上抛（否则 `TaskRunConsumer` 会 `nack` 重试，`runNackTimes >= 5` 后强制 ack 且流程滞留）；
- 若节点支持重试，填充 `Task.RetryRules`（含 `times` / `doneTimes` / `delaySecondTimes`）。

**`run` 模板方法的完整行为**（`executor/Execute.java` L23-45）：

| 步骤 | 行号 | 说明 |
| --- | --- | --- |
| 查任务 | L28 | 不存在则构造一个 `FAIL` 状态的占位 Task |
| 查实例 | L36 | `instDao.findById(task.getInstId())` |
| 置运行中 | L35 | `STATE_RUNNING` |
| 计时 | L37 / L43 | `executorStartDate` / `executorEndDate` |
| 委托子类 | L38 | `runProcess(task, inst, taskDao, instLogDao)` |
| 状态归一 | L39-41 | 只要不是 `FAIL`，统一置 `SUCCESS` |
| 回传结果 | L44 | `taskProductor.sendTaskResult(task)` |

### 步骤 5：前端接入

在 `frontend/js/nodes.js` 的节点目录中新增定义（`cellType`、名称、图标、分类、默认 data 模板、属性面板 schema），设计器会自动出现在左侧节点面板。

## §4 特殊执行器复用

`TaskRunConsumer` L68-69：

```java
if (Arrays.asList(CellType.FUN_JAR, CellType.FUN_PYTHON).contains(task.getType())) {
    execute = (Execute) SpringBeanUtils.getBean(CellType.FUN_SHELL);
}
```

**同类复用模式**：若新算子与已有算子的「执行方式」一致（例如都是本机子进程、都是 HTTP 调用），可以：

1. 在 `TaskRunConsumer` 中把新 cellType 加入复用判断分支；或
2. 更优雅地：让新 Execute 实现内部委托给已有执行器。

推荐方式 2，避免修改引擎代码。

## §5 补偿算子扩展

补偿算子是**成对**的：

| 正向算子 | 补偿算子 |
| --- | --- |
| `node_outer_http` | `node_outer_httpCompensate` |
| `node_outer_dubbo` | `node_outer_dubboCompensate` |
| `node_outer_webservice` | `node_outer_webserviceCompensate` |

新增正向算子时同步提供补偿算子，并在 DSL 中由 `edge_compensate` 挂接。

**触发链路**（`TaskResultConsumer` L172-188）：

```
正向节点 FAIL
  → 找该节点的 edge_compensate 出线
  → 取 target 节点，转 Task，删除同 nodeId+loopTimes 的旧任务
  → sendTaskRun(补偿任务) → return（不再推进正常分支）
```

**补偿组（强组合）**：若需要对「一组节点」整体回滚，把相关节点同时登记到同一 `Group`：

```json
{
  "groups": [{ "id": "g1", "name": "订单组", "type": "group_compensate", "nodes": [] }],
  "cells": [
    { "id": "n1", "cellType": "node_outer_http", "groupIds": ["g1"] },
    { "id": "n2", "cellType": "node_outer_http", "groupIds": ["g1"] }
  ]
}
```

解析时 `DslParser` L167-179 会反向填充 `group.nodes`。

## §6 循环算子注意事项

若新算子可能出现在循环区间内，必须：

1. `loopTimes` 与循环推导一致（见步骤 3）；
2. 每次循环轮次生成**新任务**（`deleteByInstIdAndNodeIdAndLoopTimes` 后 `save`）；
3. 循环区间由 `DslParser.getCellIdsBetweenLoopEdge` 推导，区间内节点会在每轮开始时被重置为「待执行」。

## §7 新增节点自检清单

| # | 检查项 |
| --- | --- |
| 1 | `CellType` 常量已定义，字面值符合命名规范 |
| 2 | Cell 子类有默认 `cellType` 初值、无参构造、完整 getter/setter |
| 3 | `TaskInterface` 实现的 Bean 名 = `cellType + "_task"` |
| 4 | `Execute` 实现的 Bean 名 = `cellType` |
| 5 | `Task.type` 被赋值为 `cellType` |
| 6 | `loopTimes` 推导与引擎一致 |
| 7 | 成功/失败都会调用 `sendTaskResult` |
| 8 | 失败状态为 `Task.STATE_FAIL` |
| 9 | 有补偿需求时配套补偿算子 + `edge_compensate` |
| 10 | 前端节点目录已登记 |
| 11 | DSL 校验规则仍满足（见 02 文档 §7）|

## §8 不做后端的替代方案

在 `web` 模块行为固定的前提下（DSL 硬编码读 `hrh_http.json`），若希望在**不写后端代码**的情况下验证新流程：

1. 在 `frontend/` 设计器中编排流程；
2. 用设计器的「导出 DSL」导出 JSON；
3. 将 JSON 覆盖到 `main/src/main/resources/hrh_http.json`；
4. 重启服务并按 [05-REST接口说明](05-REST接口说明.md) 调用运行接口。

> 前端设计器导出的 JSON 结构严格遵循 [02-DSL规范](02-DSL规范.md)，可直接作为引擎输入。
